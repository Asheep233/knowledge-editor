评分逻辑：这是一个明显高于平均 Alpha 水准的项目。核心数据路径（原子写入、写前快照、崩溃恢复草稿、路径穿越防护、删除保护）实现正确且有针对性测试；文档与代码高度一致，抽查的 Phase 报告声明均能在代码中验证。扣分集中在三处：① SQLite 单连接跨线程共享无锁（P1）；② 前端保存请求无序列化导致的竞态窗口（P1）；③ 发布工程几乎缺失——无 release workflow、CI 不构建桌面端、无 Rust 测试（P1，发布质量 55 分的主因）。Markdown 数据不可逆丢失风险经多层防护后评估为低，未发现 P0。

第二部分 · Executive Summary

“这个 v1.0.0 到底能不能放心给真实用户使用？”

  • 作为开发者自用 / Alpha 内测：可以用。 数据模型纪律性强——Markdown 为唯一事实源、SQLite 仅作可重建索引，写盘走 temp+os.replace 原子写，历史版本写前快照、崩溃恢复草稿覆盖保存窗口，用户 Markdown 不可逆丢失的路径被防护得相当好。
  • 作为公开发布给普通用户的产品：还不行。 三个硬伤：(1) 仓库内没有发布流水线，CI 只跑 pytest + vitest + 前端 build，桌面端（Rust/Tauri）完全不进 CI，安装包能否构建、升级后旧数据是否安全均无自动验证；(2) 后端 SQLite 连接被 FastAPI 线程池和文件监视线程并发使用且无锁，自动保存+搜索+文件事件同至时会随机 500（索引可重建，事实源不受影响，但用户会看到“保存失败”）；(3) 无单实例保护，双开会静默启动第二个后端共写同一 workspace。
  • 一句话定位：数据安全设计超出 Alpha 平均水平，并发与发布工程落后于其自身体验目标。 修完 3 个 P1 + 2 个关键 P2（保存竞态序列化、多实例互斥）即可进入公开 Beta。

第三部分 · P0 / P1 问题（共 3 项，无 P0）

P1 SQLite 单连接跨线程共享且无任何锁保护

位置backend/app/store/db.py:93-97（IndexStore.connect）＋ 全部同步路由（如 backend/app/routers/documents.py:update_article）＋ backend/app/services/fs_watch.py:58-61（后台监视线程） 证据 
# db.py
self.conn = sqlite3.connect(str(self.db_path), check_same_thread=False)
self.conn.execute("PRAGMA journal_mode=WAL")
self.conn.execute("PRAGMA synchronous=NORMAL")   # 全文件无 threading.Lock / mutex
FastAPI 的 def（同步）端点运行在 AnyIO 线程池（默认约 40 线程）；FsWatcher 在独立 threading.Thread 中消费文件事件并调用同一 store。整个 store 没有互斥锁，多线程会在同一个 sqlite3.Connection 上交错执行 execute/commit。 触发条件自动保存（PUT /api/articles）＋ 搜索（GET /api/search）＋ watcher 事件（外部改文件/附件落盘）任意两者同时到达。正常使用 3–5 分钟内即可能命中。 实际后果随机 sqlite3.ProgrammingError: Recursive use of cursors / 事务交错（A 线程的 commit 提交 B 线程写了一半的事务）→ 500。保存接口 500 时前端显示“保存失败”，但文件可能已写盘，用户重试产生重复快照与困惑。SQLite 文件本身因 WAL 不至于物理损坏，索引也可重建，故不构成数据丢失 P0。 为何测试未发现conftest.py 用单个 TestClient 串行发请求——天然单线程，永不并发。 建议最小修复：在 IndexStore 加 threading.RLock，包装 execute/commit/executemany 公共入口（upsert/delete/search 全部走带锁方法）；或改用 sqlite3.connect(..., isolation_level=None) + 每操作独立短事务 + 锁。半天工作量，风险极低。

P1 保存请求无序列化：手动保存与在途自动保存可并发写同一文档，旧内容可能最终落盘且 UI 显示“已保存”

位置frontend/src/components/layout/EditorArea.tsx:107-123（防抖自动保存回调）与 :159-174（saveNow）；后端 documents.py:update_article 无文档级锁 证据 
// saveNow 只清除【未触发】的定时器：
if (debounceRef.current) { window.clearTimeout(debounceRef.current); ... }
// 若防抖回调已进入 await saveArticle(...)（PUT 在途），saveNow 会并发发出第二个 PUT
后端两个线程同时执行 _maybe_snapshot → atomic_write → indexer.update_file，两次 os.replace 的完成顺序不确定。若“旧内容请求”后完成，磁盘最终为旧内容；前端两侧均按 editSeqRef === seq 判定 saved → UI 显示已保存、磁盘却是旧稿。 触发条件用户在自动保存恰好在途的瞬间按 Ctrl+S（3 秒防抖窗口尾部的熟练用户高频操作）；或快速切换文档时在途 PUT 与新文档保存交错。窗口小但真实存在，且“用户快速连续操作/连续输入”是本项目自列的重点场景。 实际后果最后几秒的编辑丢失且无任何提示（无冲突检测、无版本号校验）。历史快照可能留有旧稿可手工找回，但用户不知道要去找。 为何测试未发现vitest 只测纯函数（round-trip/tree/settings），EditorArea 组件与保存时序无任何测试；后端测试全部串行。 建议最小修复：前端加 savingRef（在途保存期间 saveNow 排队等待而非并发重发，完成后统一以最新 editor.getMarkdown() 再保存一次）；后端在 update_article 按 rel_path 加进程内锁。两端各约 30 行。

P1 发布工程与文档声明不符：无 release 流水线，桌面端完全不进 CI

位置.github/workflows/ 目录仅有 ci.yml；docs 中存在 Phase 7 发布报告/冻结审计报告 证据ci.yml 只含两个 job：backend（pytest）与 frontend（vitest + build）。没有 cargo test、没有 tauri build、没有 release/tag 触发的安装包构建、没有 NSIS 升级测试。Rust 侧 sidecar.rs（约 400 行进程管理代码）零测试零编译验证——一次依赖升级即可让主干桌面端构建挂掉而 CI 全绿。 触发条件任何针对 desktop/ 的提交；或按 README 指引寻找 v1.0.0 安装包的终端用户。 实际后果“发布就绪”的文档声明与仓库事实不一致（文档过度乐观的典型样本）；安装包存在性、升级安全性（旧版用户数据是否保留）完全靠手工，未经验证。 为何测试未发现不存在能发现它的测试——这正是问题本身。 建议最小修复：CI 增加 desktop job（cargo test + cargo check + tauri build --debug 冒烟）；再补 tag 触发的 release workflow 产出 NSIS。若安装包实际已在库外手工构建，请在 README 明示并附校验和。
未发现 P0 的理由（明确说明，非客套）：写盘路径为 temp 文件 + os.replace 原子替换（markdown_io.py:169-185），进程崩溃不可能产生半写文件；历史/恢复写回前先快照旧内容（history.py:63-71、drafts.py），操作可逆；删除有穿越防护 + 顶层目录保护 + 测试覆盖。“理论 local-first 实则存在不可恢复状态”的路径未找到——唯一接近的是掉电场景（见 P3-12），且有写前快照兜底。

第四部分 · P2 / P3 / P4 问题

P2 — Medium（6 项）

P2 1. 无单实例保护：双开应用静默启动第二个后端共写同一 workspace

位置desktop/src-tauri/src/sidecar.rs:71-76,357-368（find_free_port 逐端口尝试）；未使用 tauri single-instance 插件 证据实例 2 启动时 8000 被实例 1 占用 → find_free_port 顺利改用 8001 → 第二个 backend 进程打开同一个 workspace：双 fs watcher、双 SQLite 写者、runtime.json 被实例 2 覆盖（实例 1 的 PID 记录丢失，stop 脚本仅剩端口兜底）。WAL 模式下跨进程物理安全，但两实例编辑同一文档无任何冲突检测，后保存者覆盖先保存者。 后果用户双开图标后两窗口互相覆盖编辑、搜索结果时旧时新，且无任何提示。 建议接入 tauri-plugin-single-instance（官方插件，约 10 行）；或启动时检测已有健康 backend + 同 workspace 则聚焦已有窗口。

P2 2. 写盘成功但索引更新失败时返回 500：前端报“保存失败”而文件实际已保存

位置backend/app/routers/documents.py:update_article（atomic_write 成功后调用 indexer.update_file，后者抛错则整请求 500） 证据顺序为 snapshot → atomic_write → update_file → 返回。update_file 需要重新读盘 + SQLite 写入，任一失败（如 P1-1 的并发异常、文件被杀毒软件短暂锁住）→ 500，但 Markdown 已落盘。前端 catch → setSaveState('error')，用户重试 → 再次快照 + 重写（内容相同），产生一条冗余历史版本。 后果典型的“前端显示失败、后端实际成功”状态错位；用户对保存状态失去信任。watcher 之后通常会修复索引，故实害主要是 UX 与快照噪音。 建议将 update_file 包在 try/except 中：失败时记日志并仍返回 200（响应加 index_stale: true 标志），由 watcher 兜底重建。

P2 3. 保存失败仅置 'error' 状态：无错误详情、无自动重试、无升级提示（silent failure 风险）

位置EditorArea.tsx:119-121（catch { setSaveState('error') }，错误对象被丢弃） 证据catch 块不读 e，不 toast，不区分网络错误/409/500；连续失败无退避与告警。若后端已死（sidecar 重启中），用户只能看到一个红色状态标记，不知道“内容仍在编辑器内存里，恢复草稿机制已兜底”这一关键信息。 后果用户在错误状态下持续写作数十分钟毫无感知，关闭窗口时若恢复草稿逻辑再出岔（需要运行时验证），挫败感极强。正常情况下 recovery 草稿在保存前已注册，风险被大幅缓解——但用户不知道。 建议错误态展示原因 + “已自动保护为草稿，后端恢复后将自动重试”；失败后加一次延迟自动重试。

P2 4. 恢复历史版本 / 恢复草稿与本地编辑器状态和 watcher 刷新的时序竞争 推测，需要运行时验证

位置backend/app/routers/history.py:restore（先快照再写回，后端设计正确）＋ 前端恢复后的编辑器 reload 路径 + fs_watch 推送 证据后端恢复写盘 → watcher 检测外部变化 → 前端收到变更通知；同时前端恢复流程自身会 reload 文档。两条路径都调用 setKeContent 类逻辑，且恢复瞬间编辑器若处于 dirty（有未保存编辑），随后的自动保存可能把恢复前的旧内容重新写回磁盘——被用户理解为“恢复没生效”。静态分析无法确认前端是否在恢复后强制以服务器内容覆盖并清 dirty。 后果偶发“点了恢复又变回去”，难复现、难投诉。 建议恢复成功后前端应：清空 pending 防抖 → 强制 reload 编辑器 → 以显式标志抑制下一次 watcher 触发的本地刷新（或用内容 hash 比对避免回弹）。手工测试场景见第七部分 #15。

P2 5. dev 脚本固定端口与桌面端动态端口策略不一致，stop 兜底覆盖不全

位置scripts/start.ps1:13（固定 8000/5173）、scripts/stop.ps1:12-15（兜底仅匹配 8000/5173 + 命令行特征）vs sidecar.rs（8000→8001→8002 动态） 证据桌面实例占用 8001/8002 时，stop.ps1 的端口兜底扫描不到；若此时 runtime.json 又因多实例被覆盖（P2-1），残留 backend 进程只能靠用户手杀。命令行特征匹配（uvicorn app.main:app）是克制且正确的做法——这点值得肯定，但端口范围没跟上自己的动态端口设计。 建议stop.ps1 兜底扫描 8000-8002；或 sidecar 把端口写入固定位置的 discovery 文件供脚本读取。

P2 6. 后端异常处理存在“吞错 + 泛化”模式，关键路径缺乏区分

位置documents.py 等多处 except OSError: pass / 泛化捕获；前端多处 catch {} 空块 证据例如 _maybe_snapshot 快照失败被静默吞掉（历史版本悄悄缺失，用户以为有完整历史）；前端清理恢复点失败 catch { /* 忽略 */ } 有注释说明且幂等——这类是合理的；但快照失败属于应告知的降级。日志方面后端仅 uvicorn 默认输出，桌面版 sidecar 日志只 eprintln 到 nowhere（见 P3-13）。 建议快照失败至少写入结构化日志并在历史面板标“该时段版本缺失”；统一一个 logger。

P3 — Low（7 项）

P3 7. atomic_write 无 fsync：掉电/OS 崩溃可能留下空文件

位置markdown_io.py:169-185 证据temp 文件写入后未 flush+fsync 直接 os.replace。进程崩溃无碍（页缓存仍在），但掉电时 NTFS 上可能 replace 成功而数据未落盘 → 文件为空。缓解：写前历史快照与恢复草稿大概率留存前稿，且 WAL 数据库不受影响。属“最后 1% 的持久性缺口”。 建议写后 f.flush(); os.fsync(f.fileno()) 再 replace（成本每次数十毫秒，可只对 >10KB 文档启用）。

P3 8. editSeqRef 不随文档切换重置，跨文档状态判定依赖巧合

位置EditorArea.tsx:62,102,116,139-144 证据文档 A 在途保存（seq=5）时切换到文档 B：若 B 的 setKeContent 恰不触发 update，A 的保存完成回调会把 B 的状态判为 'saved'——碰巧 B 刚从磁盘加载确为 saved，结果正确但纯属巧合；一旦加载流程改动（例如加载后规范化内容触发 update），就会闪烁错误状态。 建议切换文档时重置 editSeqRef.current = 0 并将 seq 与 article.id 绑定判定。

P3 9. CSP 为 null ＋ KaTeX 渲染走 dangerouslySetInnerHTML

位置desktop/src-tauri/tauri.conf.json:25（"csp": null）；frontend/src/components/editor/nodeviews/MathNodeView.tsx:141,218 证据KaTeX 默认 trust:false 会转义危险输出，Tiptap schema 也会过滤不认识的 HTML 节点——两道既有防线使该风险在本威胁模型下很低。但 csp:null 意味着没有第三道防线，一旦未来引入任何 innerHTML 路径即裸奔。恶意 Markdown 文件（用户导入他人 .md）是现实输入源。 建议设置基本 CSP（default-src 'self'; img-src http://127.0.0.1:* data: 等），验证 KaTeX/图片加载不破。

P3 10. 本地 API 无 Host/Origin 校验，理论上可被 DNS rebinding 打穿

位置backend/app/main.py:80-89（仅 CORSMiddleware，无 TrustedHost） 证据uvicorn 绑定 127.0.0.1（正确），但恶意网页可将域名 rebind 到 127.0.0.1:8000 绕过同源策略读写 API（创建/改写/删除 workspace 内文件）。前提是用户开着软件并访问攻击者页面——个人本地软件中概率低、危害限于 workspace 目录，故 P3。 建议加 TrustedHostMiddleware 仅允许 127.0.0.1/localhost Host 头（3 行）。

P3 11. Python 依赖未锁版本 hash、无漏洞扫描

位置backend/requirements.txt（无 hash 固定）；CI 无 pip-audit / npm audit 建议用 pip-compile --generate-hashes 或至少钉住次版本；CI 加审计步骤（前端已有 lockfile 且用 npm ci，这点是对的）。

P3 12. Markdown round-trip 长尾风险：数学公式/嵌套 HTML/极端表格 需要运行时验证

位置frontend/src/editor/（ke.ts / markdown-roundtrip.test.ts / phase3-roundtrip.test.ts） 证据已有 round-trip 测试覆盖 KE 标记、模块、脚注、未知 ke-* 标记原样保留（后端亦有对应测试 test_unknown_ke_marker_preserved）——核心扩展纪律很好。但测试用例是手工挑选的代表性样本，非模糊测试：多轮（≥3 次）打开-保存循环、$$..\n..$$ 与表格/引用相邻、行内 HTML 与 KE 标记嵌套等组合存在未知退化可能。由于保存的是 Tiptap 序列化结果，首次保存即可能规范化重排未知语法（编辑过才保存，静默改动可能发生）。风险敞口：中低，但这是本项目产品承诺的核心，值得专项验证。 建议增加“打开→不编辑→保存→diff 必须为空”的守护测试集（一批真实世界 Markdown 语料），任何 diff 都视为回归。

P3 13. 桌面版无持久化日志，用户报障无可查文件

位置sidecar.rs:299-305（sidecar 输出仅 eprintln!）；dev 模式有 runtime/logs/（start.ps1），桌面版没有等价物 建议sidecar stdout/err 重定向到 app 数据目录滚动日志文件；backend 侧统一 logging 配置。

P4 — Cosmetic（3 项）

P4 14. 前端多数 catch 丢弃错误对象；后端部分函数签名缺返回类型注解

建议统一 catch (e) { ... console/log }`；对公共函数补注解。非关键。

P4 15. slugify 全非法字符标题回退 untitled，连续创建同名文档的后缀策略文档未写明（代码有唯一化处理，行为正确，仅缺文档）

P4 16. docs 中 Phase 报告存在少量自我表扬式措辞（“完美支持”类），与工程审慎语气不符；事实层面抽查未见造假

明确认可的设计（避免“为黑而黑”）

  • 原子写入实现正确：temp+os.replace+失败清理（markdown_io.py:169-185），进程崩溃不会留半写文件。
  • 路径安全做得扎实：safe_rel_path 用 resolve()+parents 校验（markdown_io.py:192-198），且有专门测试（test_safe_rel_path_blocks_traversal，含 C:/Windows、/etc/passwd、../ 用例）——比多数同类项目认真。
  • 删除保护分层：顶层目录 / .knowledgeeditor 拒删 + 404 语义 + 测试（test_delete_safety.py），“误删 workspace 外文件”有回归防线。
  • 历史与恢复均“先快照再写回”（history.py:63-71）：恢复操作本身可逆，这是很多商业软件都没做对的地方。
  • 崩溃恢复草稿覆盖保存窗口：保存前注册恢复点、成功后清除（EditorArea.tsx:114,118,171 + drafts.py），崩溃发生在任意阶段都有下一步兜底。
  • sidecar 进程管理是亮点：动态端口+占用退让、health 握手轮询、崩溃自动重启且设上限（MAX_CRASH_RESTARTS，防死循环）、stale runtime 清理、事件通知前端（sidecar.rs:288-350）。
  • stop.ps1 双重匹配（端口+命令行特征）不误杀无关进程，注释解释了每个设计决策（taskkill /T 的进程树理由）。
  • 测试文化健康：conftest 主动隔离用户真实 ~/.knowledgeeditor 配置防污染；测试断言的是用户可感知行为（保存响应必须带元信息，否则属性栏显示“—”）而非实现细节。

第六部分 · 数据安全审计

Q1：在什么情况下用户可能丢失 Markdown 数据？

场景防护现状残余风险
进程崩溃 / 被 kill原子写（不可能半写）+ 恢复草稿 + 历史快照极低
保存请求失败（500/网络）内容仍在编辑器内存 + 恢复点已注册低；但用户若直接关窗口且不点恢复提示 → 依赖恢复流程 需运行时验证关闭时是否强提醒
自动保存与手动保存并发无请求序列化中：尾部几秒编辑可能被旧内容覆盖且 UI 显示已保存（P1-2）
双实例编辑同一文档无冲突检测中（P2-1）
掉电 / OS 崩溃无 fsync，但写前快照大概率已留存旧稿低-中（P3-7）：最坏丢最近一次保存周期的改动，可从快照手工恢复
用户删除文档/目录穿越防护 + 保护目录 + 404 语义误删有意为之的文档属正常操作；未见回收站机制（历史快照是否保留已删文档的版本需要运行时验证）
Markdown 被编辑器静默改写未知标记保留策略 + round-trip 测试低-中（P3-12）：长尾语法组合未验证

Q2：在什么情况下 SQLite 与 Markdown 不一致？

  • 写盘成功、update_file 失败（P1-1 并发异常 / 文件短暂被锁）→ 索引滞后。watcher 会自愈，属短暂不一致，可接受。
  • 外部修改文件：watcher 事件驱动重索引（有 test_fs_watch.py），方向正确；事件丢失（网络盘/编辑器原子替换的两次事件竞态）时依赖手动重建端点——重建端点存在且有测试，兜底成立。
  • 多实例双写：两进程索引交错 upsert，最终以各自看到的文件为准收敛，短暂不一致后可重建。逻辑上无永久脏索引路径：update_file 对不存在文件执行 delete（indexer.py:109-114）。

Q3：是否存在无法自动恢复的状态？

结论：未发现“结构性”不可恢复状态。 SQLite 物理损坏 → 删库重建即可（设计承诺成立，重建端点有测试）；Markdown 单文件损坏（掉电空文件）→ 历史快照/恢复草稿兜底，但恢复动作需要用户手工发起（半自动）；唯一接近“静默不可恢复”的是 P1-2 竞态覆盖（旧稿覆盖新稿且无提示、无冲突记录）——这是本报告将其列为 P1 的核心理由。

第八部分 · 最值得增加的测试（按价值排序，宁缺毋滥）

自动化（优先级从高到低）

  1. 后端并发压力测试：ThreadPoolExecutor 20 线程混合调用 save/search/tree/update 持续 30s，断言零异常 + 最终索引与文件系统一致。直接暴露 P1-1，是性价比最高的一条。
  2. 同文档并发 PUT 语义测试：两个线程携不同内容并发 PUT，断言最终磁盘内容为“后发起的逻辑最新者”（引入版本号/时间戳后断言其单调）。
  3. Round-trip 守护语料库：收录 50+ 真实 Markdown 文件（数学/HTML/表格/KE 扩展混合），测试“加载→立即序列化→diff 必须为空”。任何 diff 即回归。
  4. 保存流水线故障注入：monkeypatch atomic_write/update_file 在各阶段抛错，断言响应码/文件状态/快照状态符合设计（修复 P2-2 的同时固化语义）。
  5. CI 桌面端 job：cargo test + tauri build --debug（Linux 交叉检查即可），让 Rust 代码进入编译验证。
  6. 前端 EditorArea 组件测试：模拟“自动保存在途 + saveNow”，断言网络层只产生串行请求（用 fake timers + fetch mock）。

手工测试（一次性，发布前必做）

  1. 升级演练：安装旧版 → 建数据 → 装新版 NSIS → 验证 workspace/设置/历史全保留。
  2. 崩溃恢复全流程：编辑中任务管理器杀进程（分别杀 frontend/backend/整体），逐次验证重启后恢复提示与内容完整性。
  3. 双开互踩：双实例编辑同一文档交替保存，观察覆盖行为（当前预期：后写赢、无提示——确认后决定修复优先级）。
  4. 掉电模拟（可选，条件允许）：大文档保存瞬间断电，检查文件与快照可恢复性。

第九部分 · 架构层面的隐患（现在没事，以后必然麻烦）

  1. Store 单例 + 单连接的线程模型没定型：现在靠“恰好没崩”运行。任何新增异步特性（协同编辑、多标签并行保存、后台导入）都会放大 P1-1。应尽早定型为“每请求短事务 + 连接池或全局锁”并写入架构文档。
  2. 写路径三步曲（快照→写盘→索引）无统一事务边界：各路由手工编排顺序，新端点（如未来的移动/重命名）容易漏快照或漏索引。建议提炼 write_document(rel, content, reason) 单一入口。
  3. 前后端无契约测试：OpenAPI snapshot 测试存在（test_openapi_snapshot.py，好），但前端 TS 类型是手写的，漂移只能在运行时发现。可用 openapi-typescript 生成类型一举消除。
  4. 保存语义缺版本概念：PUT 无 If-Match/版本号，任何并发写都是“最后写赢”。趁用户量小引入 updated_at` 乐观锁成本低；等出现协同/同步需求再改会伤筋动骨。
  5. 端口策略分裂（dev 固定 / 桌面动态）：所有围绕“后端在哪”的逻辑（stop 脚本、调试、文档）都会各说各话。建议统一为“动态优先 + 发现文件”。
  6. frontend 内 Markdown 逻辑与 backend 各有一份引用提取等实现（注释自称“语义一致”）：两处维护必然漂移，建议共享一份语料测试钉死行为。

最终结论

如果我是一个真实用户，今天安装 KnowledgeEditor v1.0.0，我最应该担心的前三件事是：

  1. “显示已保存，其实保存的是旧稿” —— 自动保存与手动保存（Ctrl+S）撞车时内容可能被静默回退（P1-2），没有冲突提示；配合双开应用（P2-1）概率放大。这是唯一可能让我真的丢刚写的字而毫无察觉的路径。
  2. “保存怎么老是失败？” —— 搜索/文件事件与保存并发时后端会随机报错（P1-1），且错误提示只有一个红色状态、没有原因和重试（P2-3）；多数时候文件其实已保存，但我作为用户无从知道，只能反复手动保存并失去信任。
  3. “升级新版本，我的笔记还在吗？” —— 仓库内没有任何安装包构建与升级测试（P1-3），旧数据在版本升级后的安全性完全未经验证；掉电等极端场景下最坏会丢最近一个保存周期的改动，需要自己想到去历史版本里翻（P3-7）。

—— 好消息是：这三件事的根因都已定位到具体函数，三个 P1 合计约 2–3 人日即可修复；这个项目的数据安全骨架（原子写、写前快照、恢复草稿、路径防护）值得这份投入。

附注：本报告基于 2026-08-16 对仓库 HEAD 的静态审计。标注「需要运行时验证」的条目为高置信推断而非确认事实；文档声明抽查（Phase 报告 vs 代码）共 14 项，13 项一致、1 项过度乐观（发布就绪度）。测试均指仓库内置测试，运行环境差异（PowerShell 版本、Windows 长路径、杀毒软件锁文件）未在本报告覆盖范围内。
