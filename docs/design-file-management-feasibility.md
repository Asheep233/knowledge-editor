### 1.1 删除的真实语义

| 步骤 | 实测结果 |
|---|---|
| `DELETE /api/articles/{id}` | **204**，文章 `.md` **从磁盘消失**（删除后唯一消失的条目）|
| `GET` 已删文档 | **404** |

### 1.2 ★ 恢复闭环：**已删文档可以真正恢复**（决定性证据）

```
1) 建文档            = Articles/可恢复文档.md
2) 删除              = 204
3) 文件存在?         = False          ← 磁盘上没了

```

对应注释：`backend/app/routers/history.py:63`
> 「P1-11：**允许恢复已被删除的文档**——快照是删除兜底，restore 应能重建文件（atomic_write 会 mkdir 父目录）」

**结论：回收站不需要新的存储层设计。** 现有 `Drafts/backup/{doc_rel}/{ts}.md` + 历史恢复 API

## 2. 需求①：回收站

> **⚠️ 治理前置（必须先确认）**：`docs/iteration-plan-1.1.x.md:130` 与
> `docs/release-acceptance-checklist.md:86` 均明确写着回收站「**拍板延后，不消耗迭代资源，
> 除非主理人明确立项**」。本功能等于**推翻既有拍板** → 需主理人**显式立项**后才可开工。

### 2.1 ★ 决定性发现：落点选对则**零扫描器改动**

把软删落点放在 **workspace 根级目录**（`Trash/` 或 `.trash/`）时，**索引器 / watcher / 搜索 /
标签 / `/api/tree` / 附件引用索引全部天然不可见** —— 因为它们**硬编码只枚举
`Articles` / `Modules` / `Attachments`**（`indexer.py:18-22`、`fs_watch.py:24-28`、
`references.py:14-25`、`documents.py:127-155`）。

**实测对照**（/tmp 临时工作区，同一份软删实现只换落点）：

| 探测项 | **根级 `Trash/`** | `Articles/.trash/` / `Attachments/images/.trash/` |
|---|---|---|
| watcher 事件 | **0 条** | 产生 `created` 事件 |
| `/api/tree` | **不可见** | **可见**（articles 与 attachments.images 都列出）|
| FTS 搜索 | **count=0** | **count=1**（回收站内容被搜到）|
| `/api/attachments/list` | — | **包含** |
| `/api/attachments/orphans` | — | **包含** |
| `GET /api/articles/.trash/old.md` | **400**（白名单拒绝）| — |

→ **落点不是审美问题，是「1 处配置」对「9+ 处排除」的差别。**

### 2.2 ★ 实测：软删**不撞既有测试**

在 `/tmp` 复制一份 backend 实现最小软删（新建 `services/trash.py`，三条删除端点的
`unlink`/`rmdir` 改为 move-to-`<ws>/.trash/<id>/<原rel>`），**真实仓库零改动**：

| 变体 | 结果 |
|---|---|
| 基线（真实仓库）| **314 passed / 2 skipped** |
| **A. 软删，API 面不变** | **314 passed / 2 skipped → 0 回归** ✅ |
| **B. 软删 + 4 个 `/api/trash` 端点** | **3 failed / 311 passed** —— 3 个失败**全部**在 `test_openapi_snapshot.py`（API 冻结契约，**设计如此**）|

原因：既有用例断言的是「**原路径腾空 + 索引清干净 + tree 更新**」，**不是「字节消失」**
（如 `test_v101_regressions.py:256`、`test_file_tree.py:111`）。前端 378 个用例中
**零命中**删除相关断言 → 前端改动是纯增量。

### 2.3 已有能力与两条恢复路径

| 能力 | 位置 |
|---|---|
| 删除前强制快照（文档）| `documents.py:305-317`（P1-11）|

### 2.5 新发现的**语义副作用**（必须在设计里交代）

| 项 | 说明 |
|---|---|
| **软删文档 → 其附件变孤儿** | 文档进回收站后从 `_doc_refs_index` 消失 → 其引用的附件变成「孤儿」，**可被 DELETE 删除**、也会出现在孤儿列表 → **恢复文档后引用断链**。需在孤儿检测中排除「仅被回收站条目引用」的附件 |
| **删除事件无法用 `mark_internal` 抑制** | `fs_watch.py:163-166` 的 deleted 分支**不查** `internal_marks`，且 `mark_internal` 要求文件存在 → 结构上不可能抑制。**但这不是缺陷**：前端幂等刷新处理（`App.tsx:254-258`），当前文档清理由 `App.tsx:530-533` 本地先行。**故软删无需新增抑制** |
| **确认文案必须改** | 现为**双重确认**「删除后**无法恢复**」（`LeftSidebar.tsx:264-267`）—— 软删后该文案即失真 |
| **`_FORBIDDEN_ROOT` 需加固** | 根级 `Trash` 目前只是**偶然**不可达（`_require_business_top` 顺带 400），应显式加入 `fs.py:26-29` 并写不变量测试（防后人把回收站挪进 `Articles/`，实测代价见 §2.1）|
| **退出时不可清理** | 退出是 `taskkill /F /T` 强杀（`sidecar.rs:453-483`），**无优雅 HTTP 钩子** → 保留策略只能用「启动时清理 / 显式清空 / 定时」|
| **保留策略的历史包袱** | 若做「保留天数」设置项 → 须**三处同步**（前端 schema/Rust 结构体/`from_value_lenient` 白名单），成本 +0.5 人日；并顺带接通 F2 死设置 |

### 3.3 连带影响（实测确认）

- 移动**文档**：正文内 `Attachments/...` 引用**不受影响**（工作区相对路径，实测逐字节不变）✅
- 标签：**不受影响**（tags 来自 frontmatter，`indexer.py:118,253` 重新读盘 upsert）✅
- 索引：**自动同步** ✅（见 §1.3）

### 3.4 设计空间（交互升级）

**前提认知**：move 需要的「路径变更 → 同步」链**每一环都已存在且已为 move 接好**（无需新建）：
①移动前 flush 未决保存（`App.tsx:544-555`）→ ②调后端 API（`LeftSidebar.tsx:346`）→
③后端 FS 变更 + 索引同步 + backup 历史迁移（`fs.py:326-327`、`:111-124`）→
④前端刷新文件树（`App.tsx:528`）→ ⑤若移动的是当前文档则用新路径重开（`App.tsx:534-535`）→
⑥编辑器状态随重开刷新。**缺的只是「输入目标的方式」。**

### 4.2 ★ 数据正确性缺口（代码级侦察发现；**决定「附属情况」是否可信**）

功能可行，但**真正的 blocker 不是 UI，而是引用数据本身不准确**。4 条既有缺口（均有实测证据）：

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| **(a)** | **后端不屏蔽代码区域**（前端 `maskCodeRegions` 屏蔽）| `markdown_io.attachment_refs_in` 无掩码；前端 `import-export.ts:16` 有 | 代码块/行内代码里的 `![](Attachments/x.pdf)` 被算作**真引用** |
| **(b)** | **`![]()` 路径含空格 → 完全漏配** | 实测 `![x](Attachments/files/我的 报告 v2.pdf)` → `[]`；正则非贪婪 `[^\s)]+` 在空格处截断 | 因上传**保留原始文件名**（含空格/CJK），该形态引用**看不见** |
| **(c)** | **`Drafts/` 完全不扫描** → **可删掉在用附件** | `references.py:14-25` 只扫 `Articles`+`Modules`；但 `RightPanel.tsx:364-379` 给孤儿附件**提供删除按钮**，`attachments.py:290` 的 DELETE 保护也**不查草稿** | 🔴 **数据丢失路径**：只被草稿引用的附件被判「孤儿」→ 用户点了删除 → 真在用 |
| **(d)** | **URL 编码不 decode** | 实测 `![](Attachments/files/my%20file.pdf)` 提取为含 `%20` 的字面量 | 提取到了却与磁盘真名 `my file.pdf` 匹配不上 → **静默漏配** |

**另两处结构性问题**：
- **后端有 3 份互相漂移的引用提取实现**：`markdown_io.py:336`（引用索引真源）、`import_export.py:168`（含 F07 非贪婪**回归**）、`attachments.py:220`（`references.py` 的重复实现）。新增功能有变成**第 4 份**的风险 → 设计须强制收敛到 `references.py` 单一来源。
- **`set[str]` 架构性丢弃信息**：`attachment_refs_in` 返回 `set[str]`，**引用类型与位置在提取时即丢失** → 「引用类型 / 行号 / 片段」不是加个字段，而是**改提取器返回结构 + 同步 4 处调用方**。

### 4.3 性能与规模（实测，修正我原先的判断）

| 操作 | 实测 |
|---|---|
| `_doc_refs_index`（1000 文档 / 200 附件 / 5000 引用，冷）| **79 ms** |
| `referencing_docs(单个)` | 73 ms（**每次全量重扫、零缓存**）|

**风险不在单次成本，而在调用次数模型**：前端每打开/切换文章会 `Promise.all` 打 `/list` + `/orphans`
（`RightPanel.tsx:121-134`）→ **同一份索引被算 2 次**；若「点击附件取详情」也每次现算，则随点击线性放大。

DB 现状：`store/db.py:32-44` 的 `files` 表**没有 refs 表/列**，但 `content` 已存全文 → 可先「用已索引全文现算」省掉磁盘 IO；要 O(1) 需新增 refs 表 + `_FTS_SCHEMA_VERSION` 迁移（不可逆）。

### 4.4 端点与契约约束（重要）

- **`test_openapi_snapshot.py` 冻结 36 路径** → 新增路径**必红**，需显式评审 + 更新快照。
- 通配路由 `GET /api/attachments/{rel_path:path}` 已存在，**能吃掉** `/{rel}/refs` → 新端点**必须注册在通配之前**，否则落到 `_guard_attachment_rel` → 400「非法路径」。
- **推荐不改路径、直接扩展 `GET /api/attachments/list` 的 `referenced_by` 载荷**（避免撞冻结契约）。
- `referencing_docs` **从未在任何 API 暴露**（仅 `fs.py:194/302/314` 内部用于删除保护）。
