第二部分：Executive Summary

问：v1.0.0 能不能放心给真实用户使用？

答：不能"放心"。可以用于体验和评测，但不应作为唯一知识库存放重要数据——除非用户接受"随时可能静默丢失最近几秒输入、部分格式内容、甚至（在 API 误用下）整个工作区"的风险，并自行做好外部备份。

  • 架构地基是对的。"Markdown=唯一事实源、SQLite=可重建索引"不是口号：原子写（tmp+同目录 os.replace）、保存前先快照、历史恢复可逆、索引损坏可自愈，都已在代码和测试中验证为真。
  • 但有 4 个 P0 级"静默数据丢失/损坏"缺陷，全部位于最高频的用户路径：编辑器保存会清空 frontmatter 的标题/标签/自定义字段；切换文档后按 Ctrl+Z 会把上一篇文档的内容灌进当前文档并随 autosave 落盘；切换文档/关闭窗口时最近一个防抖窗口（默认 3 秒）的输入无声丢失；后端 DELETE /api/fs/dir?path=. 可单次请求物理删除整个工作区（含全部历史版本）。
  • "外部修改防护"整条链是死的：watcher→事件轮询→前端提示链路中，前端因 stale closure 永远不会弹出提示；用户在外部编辑器改文件后继续在 KE 里编辑，autosave 直接覆盖外部修改，无任何感知。
  • 发布链路不可复现：CI 只有 Ubuntu 上的 pytest/vitest（且实测在 Linux 上 3 个安全测试必败——"CI 全绿"从未在 CI 环境成立过）；Windows 安装包由作者本机手工构建，sidecar exe（12.1MB）以二进制直接提交进 git。
  • 结论性建议：修复第四部分列出的 4 个 P0 + 接通外部修改提示 + 修好 CI 之前，不建议扩大 Alpha 分发范围；修复后可作为"有明确已知限制"的 Alpha 发布。

第三部分：P0 / P1 严重问题

每条含：位置 / 证据 / 触发条件 / 后果 / 现有测试为何没发现 / 最小修复建议。标注 ✅ 表示已通过运行时验证（前端用临时 vitest 用例复现，验证后已删除）；标注"推测"表示需运行时验证。

P0 Critical — 确定性数据丢失/损坏（4 项）

P0-1 编辑器保存会清空文档 frontmatter 中的 title / tags / 全部自定义字段 ✅已验证

位置：frontend/src/editor/ke.ts:34-37（withFrontmatter）、frontend/src/components/layout/EditorArea.tsx:113,168,195；后端佐证 backend/app/routers/documents.py:227-251

证据：保存链路为 withFrontmatter(ed.getMarkdown(), KE_VERSION)，其实现 stripFrontmatter(md) 后只写回 ke_version 一个字段；后端 PUT 将 body.content 逐字节覆盖写盘，无任何合并。而右侧"属性"面板（PUT /meta）会把 title/tags 写进 frontmatter。

export function withFrontmatter(md: string, version = KE_VERSION): string {
  const { content } = stripFrontmatter(md)
  return `---\n${KE_FRONTMATTER_KEY}: ${version}\n---\n\n${content}`   // 只剩 ke_version
}

触发条件：用户用属性面板设置过标题/标签（或文档来自 Obsidian，含任意 YAML frontmatter），随后发生任意一次自动/手动保存——几乎必现。

后果：标题回退为文件名、标签从文件中静默消失、自定义 YAML 字段全部丢失。违反"编辑器状态不能与磁盘事实源不一致/不能静默丢内容"的核心约束。

为什么测试没发现：round-trip 测试全部基于"编辑器输出→编辑器解析"闭环，从未测过"含 title/tags frontmatter 的文件经编辑器保存后字段仍在"。

最小修复：withFrontmatter 改为合并语义：保留 stripFrontmatter 解析出的全部原字段，仅更新 ke_version；或后端 PUT 改为"保 body 替换"（替换正文、保留 frontmatter）。

P0-2 切换文档后 Ctrl+Z 会把上一篇文档的内容灌进当前文档（跨文档串内容） ✅已验证

位置：frontend/src/editor/index.ts:149-151（setKeContent → editor.commands.setContent）；依赖行为 @tiptap/core setContent 未设 addToHistory:false

证据：Tiptap v3 的 setContent 实现为 tr.replaceWith(0, doc.content.size, doc2)，该事务进入 undo 栈；setKeContent 之后全仓未调用 clearHistory。运行时验证：加载文档A → setContent(文档B) → undo 后编辑器内容变回 A。

触发条件：打开文档 B（或恢复历史版本——同走 setKeContent）后按 Ctrl+Z 或点工具栏撤销。

后果：编辑器显示 A 的内容但 App 认为在编辑 B → 下一次 autosave 把 A 的内容覆盖写入 B 的文件。跨文档静默串内容，且 undo 栈保留上一篇文档全部历史可连续撤销。这是本次审计中"最隐蔽、后果最重"的前端缺陷。

为什么测试没发现：编辑器测试均单文档生命周期，无任何"加载→切换→undo"用例。

最小修复：setKeContent 内 setContent 后立即 editor.commands.clearHistory()（或 setContent 第三参传 { addToHistory: false }）。

P0-3 切换文档 / 关闭窗口丢弃未决 autosave：最近一个防抖窗口的输入静默丢失

位置：frontend/src/components/layout/EditorArea.tsx:139-144、216-220；frontend/src/App.tsx:200-211（openArticle 无未保存检查）；全仓无 beforeunload / onCloseRequested

证据：切换文档的 effect 仅 clearTimeout 不 flush：if (debounceRef.current) window.clearTimeout(...)，然后直接 setKeContent 加载新文档。恢复点登记只在保存路径内发生，防抖尚未触发时草稿不存在。窗口关闭同理：unmount 清理只清定时器。

触发条件：输入后 3 秒内（autosaveIntervalMs 默认 3000，设置里最大可调到 10 分钟）点击另一篇文档，或直接关闭窗口。localhost 下加载新文档只需几毫秒，远快于防抖窗口——高频触发。

后果：最多丢失一个完整防抖窗口的输入，无提示、无恢复草稿。讽刺的是：工作区切换/导入/关闭工作区都有 hasUnsaved 确认（App.tsx:285,344,367），唯独最高频的"文档间切换"和应用退出没有保护。

为什么测试没发现：App/EditorArea 组件层零测试；防抖/切换逻辑无任何用例。

最小修复：切换文档前 flush 保存（或至少把未保存内容登记为恢复草稿）；Tauri 侧用 onCloseRequested 通知前端 flush 后再关窗（现有 prevent_close 机制可复用）。

P0-4 后端 DELETE /api/fs/dir 传 "." 可递归物理删除整个工作区（含全部历史快照）

位置：backend/app/routers/fs.py:127-144（delete_dir）、fs.py:62-70（_guard_rel）、backend/app/services/markdown_io.py:192-198（safe_rel_path）

证据：防护链存在但有一个洞：rel = path.strip("/") 后为 "." 或 "" 时不属于顶层目录白名单检查范围；safe_rel_path 因 candidate == root 判定合法；_guard_rel 的 full != root 分支使 top="" 跳过保护目录检查 → 进入递归删除。pathlib 的 rglob("*") 会匹配隐藏文件（含 .knowledgeeditor/ 与 Drafts/backup/ 全部历史版本），最后 full.rmdir() 连工作区根目录一并删除。

触发条件：DELETE /api/fs/dir?path=.（或 path=、path=/、path=Articles/..）。正规前端不触发，但任何本机进程/恶意网页（simple request 无需 preflight）都可发起。

后果：整个知识库（文章+模块+附件+全部历史版本+恢复草稿）一次 HTTP 调用不可逆删除。无确认、无回收站、无快照兜底。同族问题：rename_dir 传 path=. 会把整个 workspace 根目录改名到其父目录下。

为什么测试没发现：test_delete_safety.py 测了 ../、受保护目录、外部路径，唯独没测"解析后等于 root"的等价路径。

最小修复：_guard_rel 与 delete_dir/rename_dir 入口显式拒绝 full == root；delete_dir 增加"目标必须在 Articles/Modules/Attachments 之下"的父级断言。

P1 High — 核心功能错误 / 明显一致性问题（13 项）

P1-1 "文档已被外部修改"提示是死功能（stale closure），且其"重新加载"路径本身也不刷新编辑器

位置：frontend/src/App.tsx:164-180（轮询 effect，依赖 [workspace?.open, workspace?.root] 且带 eslint-disable）、182-198（handleFsEvent）、267-276（handleReloadExternal）、EditorArea.tsx:139-144

证据：轮询 effect 闭包捕获的是 effect 执行时刻的 handleFsEvent；而 effect 每次执行时 article 必为 null（打开/切换工作区都会先 setArticle(null)）→ const cur = article?.id 永远 undefined → setExtModal 永不被调用。树刷新用的是稳定的 setTreeRefresh 所以表面正常，掩盖了 bug。即使修复闭包，handleReloadExternal 调 openArticle(rel) 得到相同 id，EditorArea 加载 effect 依赖 [article?.id] 不会重跑 → 编辑器内容仍不刷新。

后果：外部编辑器修改当前文档 → 无任何提示 → 用户继续编辑 → autosave 覆盖外部修改。整个 fs_watch 基建（轮询、事件队列、自身写入抑制）前端侧白做。代码推断确定性高，UI 行为建议运行时复核。

P1-2 已知 ke-* 标记 JSON 损坏或非独占行时被静默删除（与设计注释相反） ✅已验证

位置：frontend/src/editor/tokenizers.ts:53-83（JSON.parse 失败 return undefined）、262-276（KE_UNKNOWN_PATTERN 负向前瞻排除 note|module|attach|video|footnote）

证据：设计注释声称"JSON 损坏时保留原始文本"，但负向前瞻把"已知 kind + 损坏 JSON"挡在 fallback 之外；marked 将其归为 html token，@tiptap/markdown 对注释节点解析为空。运行时验证：<!-- ke-attach: {bad json} --> 独占行 → 序列化后标记整体消失；合法标记行尾追加文字 → 附件节点消失。

后果：第三方编辑器/手工编辑造成标记损坏，或用户在标记行尾写字 → 附件/视频/信息块/模块无声丢失，无任何 UI 提示。属于"打开后没有提示就破坏了 Markdown"的高优类型。

P1-3 普通 HTML 注释与原生 HTML 块在 round-trip 中被丢弃/拆解 ✅已验证

位置：@tiptap/markdown parseHTMLToken；GenericFallbackExtension 仅覆盖 ke-* 命名空间

证据：运行时验证：<!-- 普通注释 --> 序列化后消失；<div class="custom">内容</div> 只剩文本"内容"（标签/属性消失）。项目自测"未知标记原样保留"（markdown-roundtrip.test.ts:414-420）只断言了前后段落存在，未断言注释本身——测试名与实际保障不符。

后果：含 TODO 注释、从其他编辑器导入的含 HTML 文档，保存后缺块且用户不知情。无法编辑某种 Markdown 可以接受；静默破坏不能接受。

P1-4 autosave 与手动 Ctrl+S 无互斥锁，并发 PUT 乱序落盘，UI 仍显示"已保存"

位置：EditorArea.tsx:100-123（防抖保存）与 159-179（saveNow）；后端 documents.py:227-251（无 etag/mtime 前置校验，last-write-wins）

证据：两条保存路径共享 editSeqRef 但无 in-flight 锁：saveNow 只 clearTimeout 不取消在途请求；editSeqRef.current === seq 比对只修正 UI 标签，不阻止旧内容后落盘。后端亦无版本检查。

触发条件：保存 A 在途 → 用户输入/Ctrl+S 发出保存 B → A 晚于 B 到达后端 → 磁盘回退为旧内容，UI 显示已保存。localhost 乱序概率低（需运行时验证），但无机制性防护；且后端快照历史会把正确的新版本存档、磁盘留旧版，现象更迷惑。

P1-5 在途保存响应会把用户"拽回"上一篇文档并丢弃其未保存输入

位置：App.tsx:251-254（handleSaved 无条件 setArticle(doc)，不校验 doc.id 是否仍为当前文档）

触发条件：保存请求在途期间用户打开文档 B → B 加载完成 → A 的保存响应返回 → setArticle(A) → 编辑器重新加载 A，B 中已输入未保存的内容随 setKeContent 被清掉（且无草稿）。竞态窗口为毫秒级（保存前还串行 await registerRecoveryPoint 多一次 RTT），概率低但后果重。

P1-6 后端 documents / drafts 路由作用域越权：可删除/覆写工作区内任意文件

位置：backend/app/routers/documents.py:60-67（_article_path 只校验不越出 workspace）、254-261（delete_article 直接 unlink）；drafts.py:67-89（recovery 登记的 doc_path/draft_path 零校验入库）、92-145（restore 可覆写任意路径）

证据：DELETE /api/articles/Attachments/images/pic.png 直接成功——完全绕过 attachments 路由"被引用附件 409 禁止删除"的核心保护；也可删 .knowledgeeditor/settings.json、Drafts/backup/ 全部历史快照。drafts 两步构造可删除/覆写 workspace 内任意文件。

后果：层层防护（附件引用检查、受保护目录）存在单一绕过面。正规前端不触发，属"唯一防护层"失效型问题。

P1-7 递归遍历不防目录符号链接/Junction：delete_dir 可删到 workspace 之外

位置：fs.py:136-143；indexer.py:45-82；documents.py:116-126；fs_watch.py:79-93（所有 rglob 枚举均无 symlink 检查）

证据：Python ≤3.12 的 pathlib.rglob 默认跟随目录符号链接（3.13 才改默认）。workspace 内若存在指向外部的 junction（Windows 上无需管理员即可创建），delete_dir 递归 unlink 的是链接目标里的真实文件。附带：indexer 对指向外部的文件符号链接 read_text，把外部文件内容吸入 FTS 索引（搜索泄露，与 Python 版本无关）。

后果：直接违反"删除只作用于 workspace 内"的不变量。部分推测（依赖预置链接与 Python 版本语义），文件链接泄露子项确定。

P1-8 删除文档无任何兜底：不进回收站、删除前不留快照

位置：documents.py:254-261（delete 路径不调用 _maybe_snapshot）；history.py:58-59（恢复端点要求文件仍存在，删除后无法经 API 恢复）

后果：新建即删的文档永久丢失；有快照的只能去 Drafts/backup/ 手工翻找。对比目录删除、附件删除的层层保护，最高频危险操作（删文档）反而是保护最弱的。

P1-9 表格单元格内 \| 转义：序列化器自己产生的转义，解析器读不回来 ✅已验证

位置：frontend/src/editor/extensions/TableMarkdownExtension.ts:52-64（序列化 replace(/\|/g,'\\|')）；tokenizers.ts:213-217（parseTableRow 朴素 split('|')，不识别转义）

证据：运行时验证：| a | b \| c |（2 列）→ 解析成 3 个单元格，序列化输出 | a | b \ | c |——用户在表格里输入 | 即触发表格结构损坏。另 cellText 只拼纯文本：单元格内粗体/链接/公式/代码保存后全部退化为字面文本；对齐语法 :---: 序列化恒输出 ---，对齐丢失。

Q1：在什么情况下用户可能丢失 Markdown 数据？

场景严重度机制与补救

Q2：在什么情况下 SQLite 与 Markdown 不一致？

  • 保存时索引更新失败（锁/IO 错误）：文件已落盘、索引陈旧、无重试（P2）。可经 rebuild 自愈——可恢复。
  • 重建索引中途崩溃：非事务全量重建留半灌状态，运行中触发则需手动再 rebuild——可恢复。
  • 外部直接改/删 Markdown：watcher 1s 轮询增量更新索引；但 watcher 线程若因非 OSError 异常静默死亡，则索引永久停滞且无信号——需手动 rebuild，用户不知情。
  • 目录重命名且目录名含 % 或 _：update_move 的 LIKE 未转义，误删无关索引行——文件未动，rebuild 可恢复。
  • 索引库损坏：启动时自愈（关连接→删三件套→重建），有回归测试——可自动恢复，但会连带丢失恢复登记（P3-9 设计张力）。
  • 非 UTF-8 文件：indexer 静默置空内容，搜索内容悄悄丢失，无告警——修复文件后 rebuild 可恢复。

Q3：是否存在无法自动恢复的状态？

存在，4 种：
  1. P0-4 整库删除（文件+快照+索引同时消失）；
  2. P0-3 防抖窗口未决输入（从未落盘过，不存在于任何存储）；
  3. P1-8 删除从未保存过不同内容的文档（无快照可找）；
  4. P1-7 经 junction 误删 workspace 之外的用户文件。
其余不一致（索引陈旧/损坏/半灌）均可通过 rebuild 恢复——"Markdown=事实源"的架构承诺在索引层面经受住了验证，真正的不可恢复风险全部集中在"内容从未到达 Markdown 文件"或"Markdown 文件被删除"两类。

第八部分：最值得增加的测试（按优先级）

  1. 【自动化-前端】frontmatter 保留 round-trip：含 title/tags/自定义字段的文档经编辑器保存后字段完整。直接锁死 P0-1 的修复。
  2. 【自动化-前端】setKeContent 后 undo 为空：加载 A→切 B→can().undo()===false。锁死 P0-2。
  3. 【自动化-前端】EditorArea 保存链组件测试：mock client，断言 registerRecovery→save→clearRecovery 顺序、切换文档时未决防抖被 flush、保存失败进入 error 态且内容保留。锁死 P0-3/P1-5。
  4. 【自动化-后端】delete_dir/rename_dir 根路径等价输入（".", "", "/", "Articles/.."）一律 400。锁死 P0-4。
  5. 【自动化-前端】异常 Markdown 语料库：损坏 ke-* JSON、普通 HTML 注释、原生 HTML、表格 \|、脚注 }-->、BOM/CRLF——断言"要么正确编辑，要么原文保留，绝不静默消失"。这把 P1-2/3/9 与脚注问题一次性收口。
  6. 【端到端】保存中途崩溃恢复：登记恢复点后杀进程（不落盘），重启断言 recovery 列出、restore 写回且可搜索。这是产品核心数据安全承诺，目前只测了半边。
  7. 【自动化-后端】并发保存：同文档双 PUT 并发，断言最终文件=后到内容、无 .tmp 残留、无 500。验证单写者假设。
  8. 【手工/E2E】外部修改冲突：文档打开期间外部写盘→断言提示出现→选择保留/重载行为正确。修复 P1-1 后必须沉淀。
  9. 【自动化-后端】磁盘满注入：monkeypatch os.replace 抛 OSError，断言 5xx+原文件不变+无半文件（参照 import_export 已有注入模式）。
  10. 【CI 修复】给 Windows 语义用例加 skipif(sys.platform!='win32') 或修正断言，让 ubuntu CI 真正转绿——把"CI 基线"从文档修辞变成事实；并新增 Windows runner job（哪怕只跑 pytest+vitest）。
  11. 【手工】对发货 exe 做一次附件上传冒烟：验证 PyInstaller 打包包含 python-multipart（P2 推测项）。

原则：以上 11 项每项都对应一个已证实的风险，不为覆盖率而覆盖率。现有测试中最该先修的是 test_phase6.py 快照用例（flaky 且掩盖真缺陷）与 test_api.py:98 名不副实的 rebuild 用例。

第九部分：架构层面的隐患（现在没出问题，但会越来越麻烦）

  1. "每次启动/切库全量重建索引"不可扩展。当前设计把 rebuild 当日常路径而非灾难恢复路径，万级文档后启动时间线性恶化，且与"前端 4 秒放弃"叠加成启动失败。方向：启动时做增量校验（mtime/size 比对），rebuild 仅用于自愈。
  2. 恢复登记寄生于可丢弃的索引库。"SQLite 可随意删"与"recovery 表是唯一记录"本质矛盾。方向：恢复登记移入 workspace 内独立小文件/独立 db，与索引解耦。
  3. Markdown 扩展采用 HTML 注释内嵌 JSON，异常输入面天然脆弱。ke-* 标记的 tokenize/序列化/正则三套逻辑平行演进（本次已发现负向前瞻、非贪婪正则、平衡括号三种实现并存且行为不一），每加一种节点类型风险面翻倍。方向：统一为单一解析器+统一 fallback，并为"无法解析=原文保留"建立不可违反的全局不变量与语料库测试。
  4. 前后端状态双镜像、事件驱动名存实亡。Rust 已发事件前端不听、App 与 EditorArea 各持一份 saveState、外部修改靠轮询闭包——每次新增跨层交互都在堆 stale closure 风险。方向：前端建立单一事件总线/store，消灭 eslint-disable 的依赖数组。
  5. 本地 API 无认证的信任模型会随功能增长失守。现在加的是 close/rebuild（骚扰级），未来加同步、导出、执行类功能时，浏览器→localhost 的攻击面同步放大。方向：尽早引入启动随机 token（sidecar 注入前端），成本现在最低。
  6. 发布基础设施与代码成熟度严重不匹配。代码已到"可修 bug"阶段，发布还在"手工拍脑袋"阶段；仓库随每次重打包线性膨胀（12MB exe 直接入库）。方向：GitHub Actions windows-latest 上跑 PyInstaller+tauri build+签名（自签亦可），产物走 Release 附件而非 git 对象。
  7. 零日志体系。功能越复杂，silent failure 越多，而全栈（Python/Rust release/前端 catch）均无可观测性。方向：后端 logging 写 %APPDATA%\logs（目录已存在，只差写入），前端关键 catch 透传后端 /api/logs。
  8. 文档驱动的"freeze"流程存在自我确认风险。三份文档"实测确认"了代码中不存在的行为（外部文件需重建索引才出现在文件树）——说明 freeze-check 部分环节是在验证文档自洽而非验证代码行为。方向：freeze 声明必须附可执行证据（测试名/命令输出），否则降级为"设计意图"。

第十一部分：最终结论

如果我是一个真实用户，今天安装 KnowledgeEditor v1.0.0，我最应该担心的前三件事：

  1. 我打的字可能根本没被保存——输入后 3 秒内切换文档或关窗，内容无声消失且没有草稿；设置过标题/标签的文章，下一次保存就把它们抹掉。丢的不是文件，是"我以为已保存"的信任。
  2. 编辑器可能悄悄改写我没碰过的内容——按一次 Ctrl+Z 可能把另一篇文章灌进当前文档；我粘贴的 HTML 注释、写坏的标记、表格里的竖线，保存后可能整块消失，全程无任何提示。
  3. 出问题时我和开发者都无从查起——桌面版没有任何日志，外部修改防护是哑的，双开应用会互相杀后端；而整个安装包来自一台作者自述"有幽灵文件和杀软拦截"的机器，没有任何 CI 能复现它。

一句话：这是一个地基正确、但门窗还没装好的 Alpha——架构值得继续投入，但 v1.0.0 只适合"有外部备份的试用者"，不适合"把知识库托付给它的人"。修完第十部分"必须修"的 7 项，这个判断可以翻转。
