第一部分：总体质量评价

综合评分 72 / 100（Alpha 基线）。这是一个文档与工程纪律显著高于同类个人项目、核心架构（Markdown 唯一事实源 + 可重建索引）方向正确、但在“元数据持久化”和“首启/运行时的竞态”上存在真实 P1 缺陷的作品。评分如下：

维度分数说明
功能正确性70编辑/读写/搜索/附件主链路可用，但“属性面板标题/标签会被下一次正文保存静默擦除”属于核心功能错误。
可靠性68原子写入、崩溃恢复、索引可重建做得好；但 autosave 竞态、外部修改检测失效、首启基址注入超时窗口过短拖累可靠性。
数据安全65“Markdown 唯一事实源”原则基本成立；但标题/标签元数据丢失、文档/目录永久删除无快照、自动保存会改写文件 mtime 等，导致“看起来安全，实际存在不可逆损失”。
安全性75路径穿越防护一致、附件孤儿保护到位；但 csp:null、shell 权限过宽、附件导入不设扩展名白名单，属本地单用户威胁模型下中低风险。

测试质量62后端 pytest（102 项）+ 前端 vitest（70 项）覆盖 happy path 与格式往返，但缺少数据一致性/竞态/端到端恢复测试，且 Tauri/Rust 层在 CI 中完全未测。

第二部分：Executive Summary

这个 v1.0.0 能否放心给真实用户使用？

能谨慎地用于“自己写文章、存本地 Markdown”这一核心场景，但不建议把它当作已经足够稳的正式生产力工具。最需要警惕的不是丢失整篇正文——正文通过原子写入 + 可重建索引 + 崩溃恢复兜底，保护得相当好——而是“你以为保存了、其实被覆盖了”的元数据丢失和“应用看起来连不上后端”的启动竞态。

一句话总结：架构方向是对的，局部实现有真伤；作为 Alpha 定位合理，但距离“放心日用”还差一轮针对数据一致性和竞态的修复与回归。

第三部分：P0 / P1 问题

未发现需要立即下架或会“必然”导致整篇正文不可逆丢失的 P0。以下为 P1（高概率/高影响核心缺陷）。

P1 — High · 数据一致性 · 静默元数据丢失
属性面板编辑的「标题 / 标签」会被下一次正文保存（自动保存）静默擦除
位置：frontend/src/editor/ke.ts 的 withFrontmatter()；frontend/src/components/layout/EditorArea.tsx 的 handleUpdate/saveNow（L113/L168/L195/L205）；后端 backend/app/routers/documents.py 的 update_article_meta → markdown_io.set_meta。
证据：正文保存统一走 withFrontmatter(editor.getMarkdown(), KE_VERSION)。该函数实现为 const { content } = stripFrontmatter(md); return "---\nke_version: 1\n---\n\n" + content——先剥离全部 frontmatter，再只重写 ke_version。而属性面板保存走 updateArticleMeta → 后端 set_meta 把 title/tags 写入 frontmatter。两条链路互相不知情。
触发条件：打开文档 → 在右侧「属性」修改标题或标签并点「保存属性」→ 再编辑正文（或什么都不做等 3 秒自动保存）。
实际后果：frontmatter 里刚写入的 title/tags（以及任何自定义 frontmatter 字段）被正文保存覆盖为只剩 ke_version: 1。树/搜索里的标题回退为文件名或首个 # 标题，标签从标签列表与搜索中消失。用户无任何提示。
为什么现有测试没发现：后端 test_api.py 的 CRUD 用 content="# 测试文章..." 无 frontmatter；前端 markdown-roundtrip.test.ts 只测 node 级往返，不测「属性元信息 + 正文保存」的跨接口组合。这是一个典型的“接口各自单测通过，组合即失败”的空白。
建议：保存正文时保留并合并 frontmatter（在 withFrontmatter 之外，从 article.meta 把 title/tags/created 等字段一并写回），或让后端 update_article 在写入时对已存在的 frontmatter 做合并而非整体替换。最小修复：前端保存时构造 frontmatter = { ...article.meta, ke_version: 1 } 后与正文拼接。
P1 — High · 桌面启动竞态 · 应用“看起来连不上后端”且无自恢复
前端 API 基址注入只重试约 4 秒，而后端健康握手最长可 30 秒；慢启动时前端永久显示「后端未连接」
位置：frontend/src/main.tsx 的 resolveApiBase()（10 次 × 400ms）；desktop/src-tauri/src/sidecar.rs 的 wait_health()（30s 超时）。
证据：Rust 侧 spawn_sidecar 只有等到 wait_health 返回 ok（最长 30s，含 workspace 结构初始化 + SQLite 全量重建）后才把 RuntimeInfo 写入 SidecarState.info。在此之前 get_runtime_info 返回 Err("后端尚未就绪")。前端 resolveApiBase 对 invoke('get_runtime_info') 只重试 10 次 × 400ms ≈ 4 秒，失败后写空基址，App 的 getHealth() 落到相对路径 /api/health（release 下 origin 是 tauri.localhost，没有 Vite 代理）→ 永远失败。
触发条件：首次启动或升级后，workspace 文档量大（索引重建耗时 > 4s）或磁盘慢/杀软扫描拖慢 sidecar 启动。
实际后果：界面显示「后端服务未连接」，且没有任何重新注入机制（健康检查每 10s 轮询但用的是同一个空基址），用户只能重启应用，而重启后大概率重复同样结果，形成“大 workspace 用户无法进入应用”。
为什么现有测试没发现：冒烟均在“后端 1 秒内就绪”的干净小 workspace 上进行；M3.1 只修了“IPC 未就绪”竞态，把重试从 1 次改成 10 次，但未对齐后端 30s 的最坏启动时长。
建议：把前端重试窗口拉长到 ≥ 后端最坏时长（如 40 次 × 750ms），并/或在 health 轮询里发现后端恢复后重新注入基址；更稳妥的是 Rust 侧在 health 未就绪时返回“等待中”并让前端持续订阅 ke:runtime-ready 事件。
P1 — High · 竞态 · 潜在“旧内容覆盖新内容”
自动保存与手动保存可并发发起两个 PUT，无版本/序号保护，后者可能被先到后写的旧内容覆盖
位置：frontend/src/components/layout/EditorArea.tsx 的 handleUpdate（防抖自动保存）与 saveNow（手动保存）；后端 backend/app/routers/documents.py 的 update_article（last-write-wins）。
证据：自动保存到期触发后，const md = withFrontmatter(ed.getMarkdown()) 是发起时的快照，随后 await saveArticle(...)。若此时用户继续输入并立即 Ctrl+S，saveNow 又发起一次携带更新内容的 PUT。两次 fetch 并发，后端同步端点经线程池并发处理，写盘顺序由到达顺序决定，无 etag/版本号/序号保护。
触发条件：3 秒空闲触发自动保存 → 自动保存的 PUT 尚在途（本地慢/杀软/大文件）→ 用户继续输入 → 立即 Ctrl+S。
实际后果：若“旧内容”的 PUT 最后落盘，会静默覆盖“新内容”，用户最新的若干字丢失。概率不高但后果为不可逆内容丢失。
为什么现有测试没发现：无并发保存测试；后端测试是同步单请求。
建议：保存请求携带单调递增的编辑序号（已有 editSeqRef），后端或前端用序号做“只接受不小于当前已保存序号”的写入门卫；或在发起新保存前 abort 上一个未完成的保存。

第四部分：P2 / P3 / P4 问题

P2 — Medium

P2 — Medium
外部修改检测因 stale closure 失效：正在编辑的文档被外部改动时不会弹提示
位置：frontend/src/App.tsx 的 handleFsEvent（useCallback 依赖 [article?.id]）与文件监听轮询 effect（依赖 [workspace?.open, workspace?.root]，且 eslint-disable 抑制了依赖告警）。
证据：轮询 setInterval 在 workspace 打开时创建一次，闭包捕获了当时的 handleFsEvent（此时 article 为 null）。之后打开文档时 article?.id 变化会让 handleFsEvent 重新创建，但 interval 仍调用旧实例，于是 cur = article?.id 恒为 null，ev.type==='modified' && ev.rel===cur 永不成立。
触发条件：在 KE 中打开文档 A，同时用外部编辑器修改 A。
实际后果：「文档已被外部修改」弹窗不出现；用户继续在 KE 里编辑并自动保存，会静默覆盖外部修改。文件树对 create/delete/rename 的自动刷新不受影响（那些分支不依赖 article）。
为什么现有测试没发现：该行为需要真实文件系统 + 真实轮询时序，现有 vitest 为纯函数/组件级，无此类集成测试。
建议：把 article?.id 放进轮询 effect 依赖，或用 ref 保存当前文档 id 供 handleFsEvent 读取。
P2 — Medium
打开/切换文档会触发一次“多余”的自动保存，改写文件并更新修改时间
位置：frontend/src/components/layout/EditorArea.tsx 的文档切换 effect（setKeContent）与 handleUpdate。
证据：setKeContent 调用 editor.commands.setContent(...)，Tiptap 默认 emitUpdate=true，会同步触发 onUpdate → handleUpdate → editSeqRef++、置 dirty、并安排 3 秒后的自动保存。随后 effect 里 setSaveState('idle') 把 UI 状态改回 idle，但自动保存定时器已排定。
触发条件：每次打开或切换文档，不做任何编辑，等待 3 秒。
实际后果：文件被重新序列化并写回，updated_at/mtime 变化；若 Markdown↔模型往返存在任何轻微漂移，还会额外产生一份历史快照。用户“打开看看”也会改动文件修改时间。
为什么现有测试没发现：无“打开文档不改动 → 断言文件 mtime/hash 不变”的测试。
建议：加载内容时用 setContent(md, { emitUpdate: false })，或在 handleUpdate 里用“加载锁/首次加载标志”抑制程序性 setContent 的 update 事件。
P2 — Medium
文档/目录删除为永久删除，无回收站、无删除前快照
位置：backend/app/routers/documents.py 的 delete_article（full.unlink()）；backend/app/routers/fs.py 的 delete_dir（递归 unlink/rmdir）。
证据：两条删除路径都直接删除文件系统实体，既不写入 Drafts/backup 快照，也不进入任何回收站。前端虽有二次确认（诚实提示“删除后无法恢复”），但无兜底。
触发条件：误删文档或含多篇文档的目录。
实际后果：内容不可恢复。与“历史版本可恢复”“崩溃可恢复”的产品气质不一致。
建议：删除前 history.snapshot 一份到 Drafts/backup/{rel}（或引入回收站目录），至少保留一次可逆机会。
P2 — Medium
CI 的 push 分支为 main，但仓库默认分支是 master，推送不会触发 CI；且 Rust/Tauri 层完全未接入 CI
位置：.github/workflows/ci.yml（branches: [main]）；CHANGELOG 记录默认分支为 master。
证据：ci.yml 只在 main 分支 push 与 PR 时触发；默认分支为 master，日常推送不会跑测试。且只有 backend(pytest) 与 frontend(vitest+build) 两个 job，desktop/src-tauri 的 Rust 代码（sidecar/settings/menu 的 cargo test）与 NSIS 打包、安装/卸载验证均不在 CI 中。
实际后果：CI 形同虚设（主分支不触发），且整个桌面壳层在无人值守下无任何回归保护。
建议：把 branches 改为 [master]（或同时列两个）；新增 Rust job（cargo test，必要时 cargo build --release --no-bundle）。
P2 — Medium（需运行时验证）
退出清理的优雅终止只针对 sidecar 引导进程 PID，PyInstaller onefile 的实际 Python 子进程可能成为孤儿
位置：desktop/src-tauri/src/sidecar.rs 的 cleanup_on_exit 与 is_alive。
证据：info.pid = child.pid() 是 PyInstaller onefile 的引导进程。优雅阶段 taskkill /PID pid（无 /T）只杀引导进程；随后轮询 is_alive(pid) 检测的是引导进程，若引导进程先退出而真正承载 uvicorn 的子进程仍在，则跳过 kill_tree，子进程泄漏并持续占用端口。文档声称的“退出无残留”是通过 /T /F 强杀路径验证的，未必覆盖“引导进程先退出”的分支。
建议：优雅阶段直接按进程树终止（taskkill /T），或轮询时同时检查端口占用者。
P2 — Medium · 安全
WebView 关闭 CSP（csp: null）且授予前端过宽的 shell 权限，附件可被服务为任意内容类型
位置：desktop/src-tauri/tauri.conf.json（security.csp = null）；capabilities/default.json（shell:allow-spawn/allow-execute）；backend/app/routers/attachments.py 的 get_attachment（FileResponse 按扩展名猜 content-type）；import_package 不设扩展名白名单。
证据：上传有扩展名白名单，但 zip 导入不设白名单，可带入 .html/.svg 等；点击附件在新标签打开时，后端按扩展名返回 text/html 或 image/svg+xml，在 csp:null 的 WebView 语境下存在脚本执行面；同时前端窗口被授予了它其实用不到的 shell:allow-execute。
实际后果：本地单用户 + 自建内容威胁模型下风险有限，但“导入一个精心构造的 zip → 打开其中的 HTML 附件 → 触发脚本 → 借 shell 权限执行命令”的链条存在。属纵深防御缺口。
建议：附件读接口强制 Content-Disposition: attachment 与安全 content-type；导入对齐上传的扩展名白名单；设置最小 CSP；移除前端不必要的 shell:allow-execute。

第五部分：重点模块审计

模块评价主要问题
Frontend结构清晰、保存状态机（idle/dirty/saving/saved/error）与 editSeq 序号思路正确；但存在 stale closure、setContent 触发 onUpdate、autosave 并发等缺陷。P1 标题/标签丢失、P2 外部修改检测失效、P2 打开即触发保存。
Backend分层（router/service/store）干净，原子写入、路径防护、索引损坏重建都实现到位。删除无快照；update_article 与 get_article 内容口径不一致；依赖未锁版本。
Markdown pipelineKE 扩展 + fallback + 包裹格式设计合理，字段顺序稳定，零漂移约束明确。未知/大写标记与普通 HTML 注释的往返保留未充分验证；frontmatter 被保存链路整体覆盖（见 P1）。
WorkspaceMarkdown 唯一事实源、索引可重建、切换工作区重开索引，架构正确；迁移测试（6E.2）扎实。删除/移动/重命名用 update_move 基本无脏索引；但永久删除无兜底。
Search / indexFTS5 trigram + 外部内容表 + 触发器维护正确；短词降级 LIKE 合理。trigram 短 token 静默空结果；搜索无过期响应保护。
Attachment孤儿附件仅手动删除 + 被引用 409 保护到位；上传流式落盘。导入不设扩展名白名单；get_attachment 按扩展名服务任意内容类型。
Autosave / recovery“保存前登记草稿、成功后清除”的崩溃恢复契约实现正确；恢复/恢复历史都会先快照当前内容，可逆性好。autosave 与手动保存并发竞态；打开文档触发多余保存。
History轻量快照 + 修剪 30 份 + 毫秒命名 + 只读预览 + 恢复前确认，设计完整。快照文件名基于本地时间；删除文档不留快照。
Tauri四段式 sidecar 生命周期、崩溃自动拉起、退出清理、动态端口，实现严谨且文档验证充分。首启基址注入超时窗口过短（P1）；onefile 子进程可能孤儿（P2，需运行验证）；csp:null + shell 权限过宽。

Documentation异常诚实和完整：已知问题、决策点、约束、踩坑记录都齐全，且多数与代码一致。个别描述偏乐观：如“外部写入即时出现/检测”“未知标记不破坏文档”等，实际受 stale closure / 编辑器往返未验证限制。

第六部分：数据安全审计

在什么情况下用户可能丢失 Markdown 数据？

  • 误删文档/目录：DELETE /articles/{id} 与 DELETE /fs/dir 直接 unlink，无回收站/无删除前快照（P2）。
  • autosave 与手动保存并发：旧内容可能覆盖新内容（P1，窄窗口）。
  • 外部修改静默覆盖：外部修改检测失效，用户在 KE 中继续保存会覆盖外部改动（P2）。
  • 标题/标签元数据：被正文保存静默擦除（P1）——正文本身不丢，但 frontmatter 元数据丢。

在什么情况下 SQLite 与 Markdown 不一致？

  • 正常保存/删除/移动均通过 indexer.update_file/update_move 同步，主路径一致。
  • 外部直接写盘的文件不会即时进入索引（设计行为，文档已声明，需手动“重建索引”）。
  • 索引更新失败时（如 update_file 抛异常），文件已写入但索引未更新 → 搜索结果滞后；下次启动全量 rebuild 自愈。属可恢复，非永久不一致。

是否存在无法自动恢复的状态？

  • 永久删除：被删文档/目录无法通过现有机制恢复（唯一无法自动恢复的状态）。
  • 其余（索引损坏、frontmatter 损坏、草稿遗留）均有 rebuild/迁移/恢复兜底，属可恢复。
总体结论：核心事实源（正文）保护良好，原子写入 + 可重建索引是真正的本地优先实现；真正的短板是“删除无兜底”和“元数据/竞态导致的部分覆盖”，而不是索引或 SQLite。

第八部分：最值得增加的测试

优先级最高的自动化测试

  1. 元数据 + 正文保存一致性：模拟“PUT /articles/{id}/meta 写 title/tags → PUT /articles/{id} 存正文”，断言 frontmatter 的 title/tags/ke_version 全部保留。（直接防 P1）
  2. 打开文档不改动 → 文件 hash/mtime 不变：断言 setContent 不触发 onUpdate/不排自动保存。（防 P2）
  3. 并发保存序号门卫：用两个乱序完成的保存请求验证“旧序号不覆盖新序号”。（防 P1 竞态）
  4. 首启基址注入超时：模拟后端 5~10s 才就绪，断言前端最终仍能拿到基址并显示连接正常。（防 P1）
  5. 外部修改检测：打开文档后外部写盘，断言前端收到“已被外部修改”事件。（防 P2 stale closure）
  6. 删除前快照：删除文档后能从 Drafts/backup 恢复。（防 P2）
  7. Rust 层接入 CI：cargo test（settings 已有 8 项）+ 至少 cargo build --release --no-bundle，并把 ci.yml 分支改为 master。

第九部分：架构层面的隐患

  • frontmatter 所有权不清晰：正文保存链路（前端 withFrontmatter）与元信息保存链路（后端 set_meta）各自“拥有” frontmatter 的一部分，却没有统一的所有者，这是本次 P1 的根因，后续每加一个 frontmatter 字段都会复发。
  • “保存 = 全量覆盖”缺版本语义：文档无 etag/版本号/编辑序号保护，任何并发或乱序写都会静默 last-write-wins，随功能变多会越来越难排查。
  • 编辑器“加载/程序性修改/用户输入”未区分：setContent 与用户击键共用同一 onUpdate 通道，导致“程序改文档”被误判为“用户编辑”，后续任何自动/程序性内容注入都会触发误保存。
  • 桌面壳层零 CI：sidecar/退出清理/菜单等关键代码完全依赖人工冒烟，随版本演进回归成本陡增。
  • 附件引用提取逻辑前后端各一份正则：frontend extractAttachmentRefs 与 backend attachment_refs_in 语义需手工保持一致，容易漂移。
  • 删除语义与“可恢复”产品气质冲突：历史/崩溃都有可逆性，唯独删除没有，长期会积累用户信任问题。

第十部分：v1.0.1 修复建议

优先级内容为什么
必须修① 正文保存保留/合并 frontmatter（title/tags/ke_version）；② 首启基址注入窗口对齐后端最坏启动时长并增加恢复路径。① 静默丢失用户元数据，高频复现；② 大 workspace 用户直接进不去应用。
必须修③ 修复外部修改检测的 stale closure；④ 为保存请求加编辑序号门卫，消除 autosave/手动保存乱序覆盖。都可能导致用户内容被静默覆盖。
应该修⑤ 加载文档用 emitUpdate:false，消除“打开即触发保存”；⑥ 删除文档/目录前写一份快照；⑦ CI 分支改为 master + 接入 Rust 测试/构建。⑤ 影响文件 mtime 与用户观感；⑥ 补上唯一不可逆的删除；⑦ 让 CI 真正生效。
应该修⑧ 附件导入加扩展名白名单 + 服务时强制 attachment 头；⑨ 收窄 capabilities 权限 + 设置最小 CSP。纵深防御，成本低。
可以以后修⑩ 锁定依赖版本；⑪ 前端体积拆分；⑫ 完整深色主题；⑬ 大文档异步解析（Phase 8）。非阻塞，属打磨项。

最终结论：真实用户今天安装 v1.0.0 最该担心的前三件事

1. 改了标题/标签后继续写作，这些属性会被“自动保存”悄悄抹掉——你以为标签还在，搜索/筛选时却不见了。

2. 文档一多（索引重建慢），首次启动可能卡在“后端未连接”——不是后端坏了，而是前端等的时间太短且不会自动重连，你只能反复重启。

3. 删文档/删目录是真的永久删除，没有回收站——误删无法找回；同时如果边在别处编辑边在 KE 里保存，可能无提示覆盖外部改动。

结论：核心正文数据比想象中安全（原子写 + 可重建索引 + 崩溃恢复都做得很扎实），真正要防的是元数据丢失、启动竞态和永久删除这三类“看起来没问题、实则会后悔”的问题。
