## 1. 问题定性（实测证据）

### 1.1 编辑器管线实测（真实扩展集 + `@tiptap/markdown`）

| # | 输入 | 解析后文档文本 | 保存往返输出 | 判定 |
|---|---|---|---|---|
| **A** | `正文[^1]。` + `[^1]: 第一脚注` | `正文^1。` | `正文[^1](第一脚注)。` | ⚠️ **结构损坏**：引用变**链接**，定义行消失（文本被搬进链接目标）|
| **B** | `正文[^1]。`（无定义）| `正文[^1]。` | `正文\[^1\]。` | ✅ 内容保留（仅被转义，第二次起幂等）|
| **C** | `正文无关。` + `[^1]: 孤立定义` | `正文无关。` | `正文无关。` | 🔴 **内容消失**（工程视角的数据丢失）|

> **定性说明（依据 GFM 参考实现）**：孤立定义在 GFM **渲染层**本就不输出（`unlink`），
> 所以 marked 的行为与「渲染语义」一致——它并不是 marked 的 bug。问题在于**编辑器把渲染
> 语义当成了文档语义**：作者写下的定义文本在保存后永久消失，与产品「Markdown 单源、
> 不丢作者内容」的目标冲突。故本方案的目标是**产品保真**，而非修 marked。
| **G** | `正文[^1]。` + `[^1]: 第一段` + 缩进续行 | `正文^1。续行` | `正文[^1](第一段)。\n\n```\n续行\n```"` | 🔴 **结构错乱**：续行**变成代码块** |

> **修正（2026-09-14，依据 GFM 权威语法）**：GFM 的 `gfmFootnoteDefinitionCont = 4(spaceOrTab)`
> —— **多段落续行本就该缩进 4 空格**，`plain-export.ts:230` 的写法**是正确的 GFM**，不是 bug。
> case G 的「续行变代码块」纯粹因为 **marked 未实现脚注定义**、把缩进行当成了普通缩进代码块。
> 结论：**本方案不需要改 plain-export**，只需补解析侧。
| **H** | `正文[^note]。` + `[^note]: 命名内容` | `正文^note。` | `正文[^note](命名内容)。` | ⚠️ 同 A（命名标签同样中招）|

### 1.2 根因：CommonMark 的「链接引用定义」抢占

marked **17.0.6**（项目实际版本）对 `[^1]: 第一脚注` 的解释：

```
[^1]: 第一脚注      →  这是合法的 link reference definition
                        （label = "^1"，destination = "第一脚注"）
正文里的 [^1]       →  解析为指向该定义的「链接」，渲染 <a href="第一脚注">^1</a>
孤立定义（无引用）   →  被消费为「未被使用的定义」→ 整块 token 消失
```

对照实测（marked 直接 parse）：

| 输入 | marked HTML 输出 |
|---|---|
| `正文[^1]。` + `[^1]: 第一脚注` | `<p>正文<a href="%E7%AC%AC%E4%B8%80...">^1</a>。</p>` |
| `[^1]: 孤立定义`（无引用）| `""` ← **完全消失** |
| 行内代码 `` `[^1]` `` | `<code>[^1]</code>` ✅ 不受影响 |
| 围栏内 `[^1]: 不是定义` | `<pre><code>[^1]: 不是定义</code></pre>` ✅ 不受影响 |

**关键点**：`[^label]` 本身**不是** GFM 脚注语法被 marked 支持的特性——marked 没有内置脚注支持，它把 `[^1]` 当作**链接引用**这一 CommonMark 原生语法来处理。所以这不是「缺一个扩展」，而是**语义冲突**。

## 2. 现状盘点：谁产出、谁消费 GFM 脚注

| 路径 | 是否涉及 GFM `[^n]` | 说明 |
|---|---|---|
| **导出「普通 Markdown」** | ✅ **产出** | `plain-export.ts:230` → `[^${n}]: ${text}`；行内 `ke-footnote` → `[^n]` |
| 导出「KE 格式」 | ❌ | `keExportPayload` 保留 ke-* 方言，不受影响 |
| 导出「文档包」 | ❌ | 打包附件，正文走 KE 格式 |
| 打开/粘贴任意 `.md` | ✅ **消费** | 走同一解析链；**外部 GFM 文档、自家 plain-export 产物都走这里** |
| 「纯 Markdown 脚注样式」设置 | ❌ **不产 GFM** | `insertPlainFootnote` 实际是 `footnote` 节点 + 文末 `[n] text` 列表 —— 与我此前判断不同，**此处纠正** |
| 解析侧 | ❌ **零处理** | `grep '\[\^'` 在 `editor/` 下只命中导出代码与测试；`tokenizers.ts`/各 `*Extension.ts` **一处都没有** |

### 2.1 已有测试的盲区

`plain-export.test.ts:198` 有一条用例：

> 「marked（GFM）渲染导出的 .md：无任何 `<!--` 残留，块引用/脚注/图片结构正确」

它验证的是 **GitHub/Typora 侧能正确渲染** ✅，但**没有验证 AstraNota 自己能否读回** ❌。这个盲区正是缺陷藏身之处。

### 2.2 闭环缺口（用户可感知）

> 在 AstraNota 写脚注 → 导出「普通 Markdown」→ 归档 / 发给别人 → **再在 AstraNota 打开并保存**
> → 脚注引用变假链接 `[^1](内容)`、`<!-- ke-footnotes -->` 区域消失、多行脚注续行变代码块

## 3. 方案对比

| | **A：解析侧支持 GFM 脚注** | **B：不支持，改导出侧** | **C：维持现状 + 规范声明** |
|---|---|---|---|
| 做法 | 新增 GFM 脚注识别 → 映射到**既有** `footnote`/`footnotes` 节点 | plain-export 不再产出 `[^n]:` 定义行（降级为普通文本/列表） | 什么都不改，在 `document-format.md` 写明「不支持 GFM 脚注」 |
| 自家闭环缺口 | ✅ 消除（可回读） | ✅ 消除（不再产出该语法） | ❌ 保留 |
| 外部 GFM 文档导入 | ✅ 保留脚注结构 | ➖ 不适用（导入仍损坏） | ❌ 损坏 |
| 导出文件在 GitHub/Typora 的可读性 | ✅ 保持（仍产 GFM） | ❌ **丢失**（导出不再是脚注） | ✅ 保持 |
| 改动面 | 解析侧 + 规范 + 测试 | 仅导出侧 + 测试 | 仅文档 |
| 风险评估 | 中（新增解析规则，需消歧） | 低 | 低（但把缺陷写进规范） |
| 代价 | 打开 GFM 文件后保存会**转成 ke 方言** | 用户在外部看不到脚注 | —— |

**推荐 A**。理由：A 是唯一同时满足「自家闭环 + 外部兼容 + 不牺牲导出可读性」的方案；B 是用**主动降级产品能力**来回避问题；C 是把已知数据损坏写进规范。

## 4. 推荐方案 A：详细设计

### 4.1 映射关系（复用既有节点，不新增 Document Model）

| GFM 语法 | 映射到 | 说明 |
|---|---|---|
| `[^1]: 内容`（行首定义） | `footnotes` 节点的 `items[]` 条目 `{id, n, text}` | 与既有 ke 区域**同构**，复用 `FootnotesExtension` |
| `[^label]`（行内引用） | `footnote` 节点 `{id, n}` | 复用 `FootnoteExtension`（渲染为上标 `[n]`）|

**不新增节点类型** → 渲染器、编号维护（`maxFootnoteN`）、导出降级（`downgradeKeNodes`）全部**无需改动**。

### 4.2 ★ 核心争议：消歧规则

`[^1]` 在 CommonMark 里天然有歧义（既可能是链接引用，也可能是脚注引用）。两种策略：

| | **A1 无条件识别** | **A2 定义感知** |
|---|---|---|
| 规则 | 任何未被转义、不在代码内的 `[^label]` → `footnote` 节点 | 仅当文档中存在 `[^label]: ...` 定义时才 → `footnote` 节点 |
| 简单性 | ✅ 局部规则、确定性、易测 | ❌ 需**全文预扫**（引用可能出现在定义之前）|
| 忠实 GFM | ➖ 略激进（GFM 规定未定义引用渲染为字面文本）| ✅ 与 GFM 一致 |
| 误判风险 | `[^1]` 作为**字面文本**的文档会被误识别为脚注 | 无 |
| 逃生舱 | `\[^1]` 已转义 → 字面量 ✅ | 同 |

**采用 A2（定义感知）** —— *2026-09-14 实施期修订，原建议 A1*。理由：A1 的唯一理由是
「tokenizer 局部作用域拿不到全文定义集合」；实现形态最终确定为「解析入口全文规范化」
（见 §4.4 实现约束）后，全文上下文天然可用、该成本归零。A2 与 GFM 规范一致
（未定义引用本就渲染为字面文本）、对不含脚注定义的文档**零行为变化**、无正文误判。**故取 A2。**

### 4.3 消歧边界（拟写入规范）

| 形态 | 判定 | 依据 |
|---|---|---|
| `[^1]` / `[^note]` | 脚注引用 | 标签 = `[^` 与 `]:` 之间，允许 `[^\s\]]+` |
| `[^1]: text`（**行首**）| 脚注定义 | 必须行首（可含前导最多 3 空格）|
| `[^1]: text` 的**续行** | 并入定义 | GFM：`gfmFootnoteDefinitionCont = 4(spaceOrTab)`，**4 空格是正确写法** |
| `\[^1]` | 字面量 | 已转义 |
| `` `[^1]` ``（行内代码内）| 字面量 | marked 先消费 codespan ✅ 已实测 |
| 围栏代码块内 `[^1]:` | 字面量 | marked 先消费 fence ✅ 已实测 |
| **4 空格缩进**的 `[^1]:` | **不**识别为定义 | 缩进 ≥4 = 缩进代码块（**仅指定义起始行**，与续行规则不冲突）|
| `[^1]:` 无内容 | 定义条目标题为空 | 不 500/不丢行 |
| 标签仅数字 vs 命名 | 均支持 | GFM 允许任意标识符 |
| 重复标签定义 | 后者覆盖 / 或首个优先？| **待定**（建议：首个优先 + 保留其余为文本，避免静默丢行）|

### 4.4 实现落点

| 文件 | 改动 |
|---|---|
| `editor/tokenizers.ts` | 新增 `gfmFootnoteDefTokenizer`（**块级**，行首锚定——参照 `tableTokenizer` 的 `start: (src) => /^\[\^/.test(src) ? 0 : -1` 模式，**不要**用 `indexOf` 跨行跳转，否则会命中围栏/代码块内部）|
| | 新增 `gfmFootnoteRefTokenizer`（**行内**，与既有 `footnoteTokenizer` 并列）|
| `editor/extensions/FootnotesExtension.ts` | `markdownTokenizer` 增加对 GFM 定义块的解析分支 |
| `editor/extensions/FootnoteExtension.ts` | `markdownTokenizer` 增加对 `[^label]` 的解析分支 |
| `editor/index.ts` | 注册顺序注释需更新（新 tokenizer 与 fallback 的先后关系）|

**注册顺序风险**：`@tiptap/markdown` 用 `marked.use + unshift`（**后注册先执行**）。新 tokenizer 必须排在 `GenericFallback*` 之后注册（即比 fallback 先执行），且不得抢占 GFM 表格、公式等既有规则。→ 必须补 tokenizer 互斥测试。

### 4.5 编号与 id 稳定性

- `n` 按**定义首次被引用**在正文中出现的顺序编号 1..k（GFM 语义）；仅定义而无引用者按定义顺序追加，**保留其内容**
- `id` 需**确定性**（不能每次打开都变），否则每次保存都会重写 ke 区域 → 由归一化标签经 `keStableId` 派生

## 7. 风险与回滚

| 风险 | 说明 | 缓解 |
|---|---|---|
| tokenizer 抢占既有规则 | 新增行内/块级规则可能吃掉表格、公式、ke 标记 | 互斥测试 + 注册顺序审查；`start` 必须行首锚定 |
| **打开即改写用户文件** | GFM → ke 方言的一次性转换，会在下次保存时重写文件 | **需你拍板**；可选「首保存前提示」或「仅新版式文档才转换」 |
| `id` 非确定性 | 每次打开 id 变化 → 反复重写 | 由标签派生 id + 往返幂等测试 |
| 误判字面量 `[^1]` | A1 的已知代价 | 逃生舱 `\[^1]`；必要时降到 A2 |
| 扩大改动面 | 涉解析核心链路 | 独立批次 + 独立验证（沿用本轮 dev/verifier 分离模式）|

**回滚**：改动集中在解析侧 4 个文件 + 新增测试，回退提交即可；不涉数据迁移、不涉后端、不涉 B 层标识。
